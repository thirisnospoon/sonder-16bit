# Модель угроз

Документ обещан [ARCHITECTURE.md](ARCHITECTURE.md) §14 ещё в фазе 5 и до
сих пор не существовал. Написан он не по памяти: каждое утверждение ниже
либо измерено на поднятой системе, либо помечено как непроверенное.

**Столбец «Чем» обязателен.** Средство защиты без способа убедиться, что
оно работает, — это намерение. Так уже вышло с ограничением частоты
входа: контракт объявлял код `LOGIN_RATE_EXCEEDED`, §14 обещал предел, а
двенадцать неверных паролей подряд проходили без единого отказа.

## 1. Что защищаем

| Ценность | Почему |
|---|---|
| Пароли | Их переиспользуют в других системах; утечка вредит за пределами Sonder |
| Сессии | Токен = полный доступ от лица человека |
| Личное содержимое | Лента, профиль и посты закрыты: в этой системе публичного чтения нет |
| Целостность решений | Кто вправе удалить пост или заблокировать — решает ядро, и обойти это не должно быть возможно |
| Доступность записи | Потолок 21,5 команды/с; исчерпать его дешевле, чем защитить |

## 2. Границы и кто за ними

```
браузер ──TLS──► nginx ──HTTP──► оболочка ──нульмодем──► NODE-7
                   │                 │
                   └── статика       └── JDBC ──► Firebird
```

* **Браузер** — недоверенная сторона целиком: скрипт на странице,
  расширение, сам пользователь.
* **nginx** — публичная граница. Всё, что за ней, в локальном составе
  считается доверенным периметром.
* **Оболочка** — единственная, кто говорит с базой и с ядром.
* **NODE-7** — доменные решения. Ввода-вывода не имеет по построению
  ([ADR-0011](adr/0011-pascal-domain-core.md)), сети не видит.
* **Firebird** — состояние. Наружу порт не публикуется.

## 3. Угрозы и что им противопоставлено

### Кража сессии скриптом на странице

| | |
|---|---|
| Средство | Токен только в куке `HttpOnly`; в `localStorage` его нет вовсе |
| Измерено | `Set-Cookie: sonder_session=…; Path=/; Max-Age=43200; HttpOnly; SameSite=Strict; Secure` |
| Чем | `AuthHttpIT.loginSucceeds` сверяет ВСЕ объявленные свойства, а не факт успеха |

Контракт требовал этого с самого начала, а оболочка отдавала токен телом
ответа — расхождение прожило до первого настоящего подъёма системы.
Проверка появилась после и сверяет каждое свойство отдельно.

### Кража сессии по сети

| | |
|---|---|
| Средство | TLS на всём составе; обычный HTTP только перенаправляет; кука `Secure` |
| Измерено | `GET /` по HTTP → 301 на HTTPS; кука приходит с `Secure` |
| Чем | 21 браузерный сценарий идёт по HTTPS с настоящей кукой |
| **Не закрыто** | **HSTS не выставляется** |

HSTS сознательно НЕ включён в локальном составе: сертификат
самоподписанный, а строгая транспортная политика поверх недоверенного
сертификата делает стенд труднее открыть, а не безопаснее. **В бою с
настоящим сертификатом HSTS обязателен** — и это требование к развёртке,
которое локальная проверка подтвердить не может.

### Подбор пароля

| | |
|---|---|
| Средство | 10 неудач на ник за 15 минут, затем `LOGIN_RATE_EXCEEDED` |
| Измерено | 11-я попытка отвечает 429; верный пароль в пределе тоже не проходит |
| Чем | `AuthHttpIT` — четыре проверки, роняются снятием предела |

Счёт нечувствителен к регистру (иначе предел обходится сменой букв) и
ведётся по ЛЮБОМУ нику, существующему или нет (иначе разница ответов
выдаёт, кто в системе есть). Успешный вход стирает счёт: предел защищает
от подбора, а не наказывает за опечатку.

**Ограничение по адресу отсутствует.** Перебор редких паролей по многим
никам сразу этим пределом не ловится. Считать по адресу мешает то, что
за прокси он приходит заголовком, которому нельзя верить без доверенной
цепочки; заводить защиту, обходимую подделкой заголовка, — хуже, чем
назвать её отсутствующей.

### Перечисление пользователей

| | |
|---|---|
| Средство | Одинаковый ответ и время для существующего и несуществующего ника |
| Измерено | Медианы 266 и 263 мс — разница 3 мс, это 1 % |
| Чем | `./sonder timing` |

Код ответа и его форма одинаковы (`CREDENTIALS_INVALID`), предел попыток
считает оба случая, и время ответа теперь тоже измерено, а не выведено
из устройства кода.

**Цена этого средства известна точно.** Замер со снятым фиктивным хэшем
даёт 272 мс против 40: разница в 580 %, и перебором по ней вычисляется
весь список пользователей за то же время, что и один вход. Именно так и
выглядела бы «естественная» реализация — нет пользователя, нет и
проверки пароля.

Порог замера грубый — двадцать процентов — и это осознанно: настоящая
регрессия здесь не «на два процента», а «вшестеро», а тонкий порог на
замере, где каждый запрос платит за свежее TLS-рукопожатие, давал бы
ложные срабатывания. Проверка, падающая раз в двадцать прогонов,
сообщает о системе ровно то же, что не падающая никогда.

### Хранение паролей

| | |
|---|---|
| Средство | BCrypt |
| Измерено | `$2a$12$…` — стоимость 12 |
| Чем | `CredentialsTest` |

### Хранение токенов сессии

| | |
|---|---|
| Средство | В базе лежит SHA-256 токена; сам токен — только в куке |
| Измерено | В колонке `token_hash` шестьдесят четыре знака hex; токена нет нигде |
| Чем | `AuthHttpIT.tokenIsNotStored` — ищет токен по всей колонке и проверяет, что отпечаток не принимается как кука |

Раньше токен лежал как есть и служил первичным ключом: утечка дампа
означала угон всех живых сессий — без подбора, без следов и без
возможности заметить.

SHA-256, а не bcrypt, и разница принципиальная. Пароль человек выбирает
сам, он угадываем, и потому хэшируется нарочито медленно. Токен выдаёт
`SecureRandom`, в нём 256 бит энтропии, и перебирать его некому:
быстрый хэш достаточен, а медленный стоил бы сотни миллисекунд на
КАЖДЫЙ запрос — сессия проверяется всегда.

Соли нет намеренно: она защищает от заранее посчитанного перебора,
которого при 256 битах случайности не бывает, и потребовала бы читать
строку прежде, чем её искать.

Проверка считает SHA-256 СВОЕЙ реализацией, а не вызовом кода оболочки:
сверка вычисления с ним же подтверждала бы лишь, что код равен самому
себе.

### Обход правил домена через интерфейс

| | |
|---|---|
| Средство | Право решает ЯДРО; спрятанная кнопка защитой не считается |
| Измерено | Страница модерации показывается всем вошедшим, отказ приходит от ядра |
| Чем | Браузерный сценарий «подписка на себя отвергается ядром, а не прячется кнопкой» |

### Доступ гостя к личному

| | |
|---|---|
| Средство | Всё, кроме входа, выхода и регистрации, требует сессии |
| Измерено | Каждая закрытая операция отвечает гостю 401, и ровно они |
| Чем | `GuestAccessIT` — читает контракт и идёт по нему |

Отказ по доступу наступает РАНЬШЕ поиска: ответ «нет такого поста» гостю
рассказывал бы, чего в системе нет, и перебором таких ответов чужой
узнавал бы существующие идентификаторы.

### Выполнение чужого кода на странице

| | |
|---|---|
| Средство | CSP без `unsafe-inline`, сторонних источников нет по построению |
| Измерено | `default-src 'self'; script-src 'self'; …; frame-ancestors 'none'` |
| Чем | Браузерный сценарий «заголовки безопасности на месте» |

Проверяются и `X-Content-Type-Options: nosniff`, и `X-Frame-Options:
DENY`, и `Referrer-Policy`. Сверяется не только присутствие, но и
СОДЕРЖАНИЕ: заголовок с ослабленным значением хуже отсутствующего — он
выглядит защитой. Отдельно проверяется отсутствие `unsafe-inline`,
которое сводит CSP к украшению.

До этой проверки заголовки держались только тем, что конфигурацию nginx
не трогали, — а её правили трижды за один вечер.

### Межсайтовая подделка запроса

| | |
|---|---|
| Средство | `SameSite=Strict` на куке сессии |
| Измерено | Атрибут присутствует |
| Чем | `AuthHttpIT.loginSucceeds` |

Отдельного токена CSRF нет и не требуется: `SameSite=Strict` не даёт
браузеру приложить куку к запросу, начатому с чужого сайта.

### Утечка подробностей в ответах

| | |
|---|---|
| Средство | Наружу уходят только код и `traceId`; стек и сообщение исключения — в лог |
| Измерено | Неизвестный маршрут и кривое тело отвечают конвертом контракта |
| Чем | `GuestAccessIT.отказВсегдаПоКонтракту` |

### Доступ к внутренним ручкам

| | |
|---|---|
| Средство | nginx отдаёт 404 на `/actuator` |
| Измерено | `/actuator/health`, `/actuator/prometheus`, `/actuator/env` — все 404 снаружи |
| Чем | Браузерный сценарий «внутренние ручки наружу не выходят» |

### Исчерпание записи

| | |
|---|---|
| Средство | 20 постов в час на человека; за коленом система отказывает названным кодом |
| Измерено | Потолок 21,5 к/с; дальше `DECIDER_UNAVAILABLE` по таймауту 5 с |
| Чем | `./sonder bench` |

Потолок принадлежит линии и не масштабируется машинами
([BENCHMARK.md](BENCHMARK.md)). Это делает отказ в обслуживании дешёвым:
восьми потоков достаточно, чтобы очередь к ядру начала переполняться.
Смягчает только доменная квота — и только против одного пользователя.

## 4. Чего эта модель НЕ покрывает

Перечислено затем, чтобы отсутствие было решением, а не умолчанием.

* **Доверенный периметр за nginx.** Всё внутри составной сети считается
  своим: линия к ядру не шифруется, IIOP не аутентифицируется, порт базы
  не публикуется наружу и защищён только этим.
* **Целостность цепочки поставки.** Образы тянутся по тегам, подписи не
  проверяются, сканера уязвимостей нет ([ENGINEERING.md](ENGINEERING.md)
  §2, раздел «чего нет»).
* **Секреты.** Пароль базы приходит переменной окружения с умолчанием
  `masterkey` — годным только для локального состава.
* **Приватность содержимого от администратора.** Всё лежит в базе
  открытым текстом; шифрования на уровне записей нет.
* **Устойчивость самого DOSBox.** Ядро исполняется эмулятором; его
  собственные уязвимости в модель не входят.

## 5. Что делать дальше, по убыванию пользы

1. HSTS в боевой развёртке.
2. Ограничение частоты по адресу — вместе с доверенной цепочкой прокси,
   без которой оно обходится подделкой заголовка.
Закрыто с первой редакции этого документа: хранение отпечатка вместо
токена, проверки на заголовки безопасности и невидимость актуатора,
измерение равенства времени ответа.
