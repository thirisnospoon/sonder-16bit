# Архитектура Sonder

> Статус: черновик 2. Изменения — через ADR в `docs/adr/`.
>
> Черновик 1 помещал доменное ядро в Java, а DOS-ноду делал вторым клиентом
> с текстовым интерфейсом. [ADR-0011](adr/0011-pascal-domain-core.md) это
> изменил: ядро переехало в Pascal, интерфейса у DOS-ноды больше нет.

## 1. Принципы

1. **Ни одна поверхность не выглядит старой.** Абсурд живёт в архитектуре, не в оформлении.
2. **Каждая нелепость несёт нагрузку.** Технология без реальной работы в системе удаляется.
3. **Контракт первичен.** Схемы в `contracts/` — единственный источник правды; код генерируется из них.
4. **Домен не знает о транспорте.** Гексагональная архитектура: одно ядро, N адаптеров.
5. **Ошибка — это значение.** Никаких «упало и ладно» ни в Java, ни в Pascal.
6. **Всё, что не проверено тестом в CI, считается сломанным.**

## 2. Тезис

**Бизнес-логика современной соцсети исполняется шестнадцатибитным кодом
под DOS.**

React, Firebird и Java — это ввод-вывод: принять запрос, достать данные,
сохранить результат, разослать события. Решения — «можно ли этому пользователю
создать пост», «свободен ли ник», «разрешено ли это действие модератору» —
принимает Turbo Pascal.

Отсюда же и архитектурная форма: **функциональное ядро, императивная
оболочка**. Ядро детерминировано и не делает ввода-вывода не из эстетических
соображений, а потому что под DOS его сделать нечем.

## 3. Единицы развёртывания

| Юнит | Технология | Ответственность |
|---|---|---|
| `web` | Свой реактивный слой на сигналах, TS + Vite, nginx | Современный веб-клиент и админка ([ADR-0012](adr/0012-own-reactive-core.md)) |
| `core` | Java 8, Spring Boot 2.7 | Оболочка: REST, сессии, загрузка состояния, сохранение решений. Порты: REST, IIOP, JDBC |
| `events` | Java 8, Spring Boot 2.7 | Дренаж outbox, CQRS-проекции, SSE-фанаут |
| `gateway` | Java 8, Netty | Мост «SOAP ↔ последовательная линия»: кадрирование, мультиплексирование, метрики NODE-7 |
| `dosnode` | DOSBox + FPC `i8086-msdos` | **NODE-7: доменное ядро.** Принимает команды, возвращает решения |
| `db` | Firebird 5 | Хранилище, шина событий, очередь outbox ([ADR-0013](adr/0013-firebird-and-orm.md)) |
| `obs` | Prometheus + Grafana + Loki | Наблюдаемость (профиль `observability`) |

Spring Boot 2.7 — последняя ветка с поддержкой Java 8. Java 8 — последний JDK,
несущий CORBA в составе; в Java 11 она удалена. См.
[ADR-0004](adr/0004-corba-iiop.md).

## 4. Топология

```
                    ┌──────────────┐
                    │     web      │  свой реактивный слой
                    └──────┬───────┘
                     REST + SSE
                           │
                    ┌──────▼───────┐        IIOP        ┌──────────────┐
                    │     core     │◄───────────────────┤    events    │
                    │              │   обогащение       │              │
                    │  ОБОЛОЧКА    │                    │ outbox drain │
                    │              │                    │ проекции CQRS│
                    │ REST · сессии│                    │ SSE fanout   │
                    │ загрузка     │                    └──────┬───────┘
                    │ состояния    │                           │
                    │ сохранение   │                           │ JDBC
                    │ решений      │                           │ события
                    └───┬──────┬───┘                           │
                        │      │ JDBC                          │
              SOAP-клиент      └───────────┐                   │
                        │                  ▼                   ▼
                  ┌─────▼──────┐    ┌──────────────────────────────────┐
                  │  gateway   │    │            Firebird             │
                  │            │    │ write model │ outbox │ read model│
                  │ SOAP ↔ линия│   └──────────────────────────────────┘
                  │ кадры · mux│
                  └─────┬──────┘
                        │  1 линия, 11 520 Б/с, кадры по 512 Б
                  ┌─────▼──────┐
                  │  dosnode   │
                  │  NODE-7    │   ДОМЕННОЕ ЯДРО
                  │            │   команда + состояние → решение
                  │ TurboCore  │   файбер на команду
                  └────────────┘
```

Направление SOAP: **Java — клиент, NODE-7 — сервер**. Гейтвей терминирует
SOAP со стороны Java и превращает вызовы в кадры на линии.

## 5. Контракты как источник правды

```
contracts/
├── soap/decider-v1.wsdl + xsd/      → CXF wsdl2java  → core (Java, клиент)
│                                    → tools/wsdl2pas → dosnode (Pascal, сервер)
├── idl/enrichment-v1.idl            → idlj           → core, events
├── openapi/social-v1.yaml           → openapi-typescript → web
├── events/*.schema.json             → схемы полезной нагрузки outbox
└── errors/errors.yaml               → Java enum, TS union, Pascal-константы
```

Каждая операция WSDL описывает три вещи: команду, **состояние, необходимое для
решения**, и форму решения. Объявление состояния — часть контракта, а не
соглашение: `core` не имеет права послать команду, не приложив всего, что
объявлено. Иначе ядро примет решение по неполным данным.

**Проверка дрейфа.** CI перегенерирует все стабы и падает на
`git diff --exit-code`. Ручная правка сгенерированного кода невозможна by design.

**Версионирование.** Версия в имени (`-v1`). Совместимые изменения — добавление
опциональных элементов. Ломающие — новая мажорная версия рядом со старой.
Golden-файлы предыдущих версий держатся в CI.

## 6. Доменная модель

Агрегаты: `User`, `Post`, `Comment`, `Follow`, `Session`, `ModerationAction`.

```
User 1──* Post 1──* Comment
User *──* User (Follow)
User 1──* Session
Admin 1──* ModerationAction ──► User | Post
```

**Инварианты живут в Pascal**, и нигде больше:

- ник уникален, `[a-z0-9_]{3,20}`, регистронезависимо;
- забаненный пользователь не создаёт контент, но его сессии остаются валидными до явного отзыва;
- пост нельзя удалить дважды; удаление идемпотентно;
- нельзя подписаться на себя;
- модераторское действие всегда порождает запись аудита;
- ограничения частоты по аккаунту и по адресу.

Роли: `USER`, `MODERATOR`, `ADMIN`. Проверка прав — тоже в Pascal. Java не
дублирует ни одно из этих правил: продублированное правило рано или поздно
разойдётся со своей копией.

## 7. Путь записи

```
POST /api/posts
  │
  ├─ core: проверка сессии, разбор формы
  ├─ core: загрузка состояния, объявленного контрактом
  │        (бан-статус автора, счётчики частоты, занятость ника, версия агрегата)
  │
  ├─ SOAP CreatePost(команда, состояние) ──► gateway ──► NODE-7
  │                                                        │
  │                                       применение правил, без ввода-вывода
  │                                                        │
  ◄─────────── Решение ────────────────────────────────────┘
  │            принято: перечень доменных событий
  │            отказ:   код ошибки из errors.yaml
  │
  ├─ отказ  → 4xx клиенту, ничего не сохраняется
  │
  └─ принято → одна транзакция:
                 write model (с проверкой версии агрегата)
               + строка в outbox
               + аудит
               COMMIT
               → триггер шлёт POST_EVENT outbox_new
```

**Оптимистическая блокировка обязательна.** Состояние загружено до вызова и
могло устареть за время круга по линии — а это десятки миллисекунд. При
расхождении версий команда переигрывается целиком, включая новый вызов ядра.

**Потолок записи.** Круг по линии — это команда и решение, вместе примерно
600–800 байт, плюс 13 мс фиксированных накладных. При 11 520 Б/с на направление
это порядка **десяти операций записи в секунду на всё приложение**. Число
измерено (S2), а не оценено, и является главным узким местом системы.
Конвейеризация файберами улучшает его примерно вдвое.

## 8. Путь чтения

**Чтение не касается NODE-7 вообще.** Запросы обслуживаются денормализованными
таблицами read-model, которые наполняет `events` из outbox. Ограничение линии
на чтение не распространяется.

Это не оптимизация, а условие жизнеспособности: если бы лента шла через
последовательную линию, приложение упёрлось бы в десять чтений в секунду.

Согласованность чтения — eventual, лаг измеряется и вынесен в SLO (§12).

## 9. Событийный конвейер

```
COMMIT в core
    │
    ├─► POST_EVENT outbox_new            (дверной звонок, без данных)
    ▼
events: подписка на событие отдельным соединением (вне пула)
    │   + poll-фолбэк раз в 1 с — корректность не зависит от NOTIFY
    ▼
SELECT … FROM outbox WHERE status='PENDING'
  ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 64
    │
    ├─► обогащение: IIOP-вызов в core
    ├─► обновление read model
    └─► SSE-фанаут в web
    ▼
status='DONE' | retry с экспоненциальным backoff | 'DEAD' после N попыток
```

**Почему нельзя просто NOTIFY.** Полезная нагрузка меньше 8000 байт;
уведомления не долговечны и теряются при отключении слушателя; одинаковые
уведомления в транзакции схлопываются; очередь общая на кластер и конечна —
залипший слушатель ломает `NOTIFY` для всех; pgjdbc получает уведомления только
при опросе на соединении вне пула. Поэтому `POST_EVENT` — исключительно сигнал
пробуждения, а корректность обеспечивает outbox. См.
[ADR-0003](adr/0003-outbox-over-notify.md).

**Гарантии.** At-least-once, потребители идемпотентны по `event_id`. Порядок
гарантирован только внутри одного `aggregate_id`. После восьми неудачных попыток
строка помечается `DEAD`, растёт `sonder_outbox_dead_total`, срабатывает алерт.

## 10. Роль CORBA

`events` строит проекции только на том, чем владеет сам
([ADR-0016](adr/0016-events-owns-its-data.md)). Отсюда две разные тактики.

**Содержимое агрегата — синхронным вызовом по IIOP**
(`contracts/idl/enrichment-v1.idl`). Тело поста, ник автора, время создания
принадлежат `core`; ответ нужен один на событие и он маленький. Если `core`
недоступен, дренаж outbox честно останавливается и ретраится, а не пишет
неполные проекции.

**Граф подписок — своей проекцией** из событий `follow.created` и
`follow.removed`. Тянуть список подписчиков по IIOP на каждый пост упёрлось бы
в измеренный потолок дренажа (S5, около пятисот событий в секунду), а
множественный `INSERT` по своей таблице — нет.

Первая редакция этого раздела запрещала читать таблицы `core` вообще и была
написана до появления проекций. На первом же столкновении с фанаутом
выяснилось, что запрет и нарушается, и недостаточен: операции «дай
подписчиков» в IDL нет вовсе.

Практическое последствие: IIOP плохо переносит контейнерные сети — ORB зашивает
адрес в IOR. Фиксируем `ORBServerHost` и покрываем интеграционным тестом внутри
compose-сети (спайк S5).

## 11. Аутентификация и сессии

- Пароли: bcrypt (cost 12).
- Стор сессий в Firebird: `session(id, user_id, issued_at, expires_at, revoked_at)`.
- `web` получает сессию в куке `HttpOnly; Secure; SameSite=Strict`. Никаких токенов в `localStorage`.
- Проверка сессии — работа `core`: она требует обращения к базе, а ядро ввода-вывода не делает. В NODE-7 приходит уже установленная личность и её роль.
- Правила **авторизации** при этом в ядре: «может ли этот пользователь с этой ролью выполнить это действие над этим объектом» — доменный вопрос.

Разделение проходит по границе ввода-вывода: аутентификация требует базы и
остаётся в оболочке, авторизация — чистое правило и живёт в ядре.

## 12. Ошибки, трассировка, SLO

**Таксономия.** `contracts/errors/errors.yaml` — единственный список кодов, из
него генерируются Java-enum, TS-union и Pascal-константы. Категории:
`VALIDATION`, `AUTH`, `PERMISSION`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMIT`,
`UPSTREAM`, `INTERNAL`. Отказ ядра — это всегда код из этого списка.

**Трассировка.** `trace_id` рождается на входящем адаптере и живёт до конца:
HTTP-заголовок → команда → SOAP-заголовок → кадр в линии → структурный лог
NODE-7 → колонка в строке outbox. Любое решение восстанавливается по одному
идентификатору, включая то, которое принял шестнадцатибитный код.

**SLO.** Цели уточнены после бенчмарка Ф10 и сверены с измеренным.
Столбец «Чем» обязателен: цель без способа её проверить — это пожелание,
и таблица без него однажды уже описывала другую систему.

| Показатель | Цель | Измерено | Чем |
|---|---|---|---|
| REST чтение, p99 | < 150 мс при нагрузке до колена | **43 мс** (8 потоков) | `./sonder bench` |
| REST запись, p99 | < 800 мс | **242 мс** (на потолке, 4 потока) | `./sonder bench` |
| Пропускная способность записи | ≥ 10 операций/с | **21,5 к/с** без отказов | `./sonder bench` |
| Лаг read model, p99 | < 1 с | **935 мс** — запас 6,5 % | `./sonder lag` |
| Доля событий в DLQ | < 0.01 % | не измеряется | — |
| Доступность NODE-7 | > 99.5 % | не измеряется; возврат после обрыва — 40 с | `./sonder chaos` |

**Читать эту таблицу надо с оговорками, и они важнее самих чисел.**

Чтение держит цель ДО КОЛЕНА и не держит за ним: на 32 потоках p99
уже 351 мс, на 128 — 1686 мс. Полка начинается около 270 запросов/с;
всё, что дальше, — очередь, а не работа.

Лаг read model проходит по цели с запасом в шесть процентов, и запас
этот — ширина интервала дренажа. Дренаж ходит раз в секунду, поэтому
лаг распределён почти равномерно от нуля до секунды плюс время
обработки: измеренный минимум 193 мс, медиана 860 мс. Увеличение
периода дренажа или веса обогащения ломает цель немедленно.

Две последние строки не измеряются, и это записано, а не умолчано. DLQ
как отдельной таблицы нет: ядовитое событие видно по счётчику попыток в
самой очереди. Доступность NODE-7 требует длительного наблюдения,
которого на локальном составе взять негде; измерено соседнее и
проверяемое — время возвращения после обрыва линии.

## 13. Наблюдаемость

**Написанное здесь описывает то, что есть, а не то, что задумывалось.**
Прежняя редакция описывала замысел в настоящем времени, и отличить её от
отчёта о сделанном было нельзя.

- **Логи.** У оболочки — строка на каждый запрос с `trace_id` в каждой
  строке (`%X{trace_id}` в формате). У NODE-7 — файл `NODE7.LOG` на
  смонтированном диске эмулятора, который точка входа контейнера
  переносит в его вывод: `docker compose logs node` показывает и то, что
  сказало ядро. Отдельного канала мультиплексора под лог нет, NDJSON
  нет, Loki нет — сбор логов остаётся задачей эксплуатации.
- **Метрики.** Micrometer → Prometheus, `/actuator/prometheus`. Оболочка
  опрашивает NODE-7 раз в пятнадцать секунд и переиздаёт его счётчики:
  пик и ёмкость арены, занятые файберы, обслужено, отвергнуто, не
  разобралось, ошибки линии, байты в обе стороны. Плюс своё: глубина
  очереди outbox и возраст последнего ответа ядра. Времени решения p50/p99
  ядро не сообщает — часов у него нет.
- **Панель.** Grafana поднимается профилем `./sonder obs`; источник
  данных и сама панель заданы файлами, а не мышью. Пять панелей отвечают
  на три вопроса устройства: близко ли ядро к пределу арены, отстаёт ли
  проекция, жива ли линия. Панели «сколько занято линии» в процентах
  нет: занятость считается по байтам в секунду против 11 520 Б/с, и
  выводить долю из счётчика, обновляемого раз в пятнадцать секунд,
  значило бы рисовать ступеньки и звать их загрузкой.

## 14. Безопасность

- Модель угроз — [THREAT-MODEL.md](THREAT-MODEL.md). Обещана она была в
  Ф5 и написана только сейчас; каждое утверждение там либо измерено на
  поднятой системе, либо помечено как непроверенное.
- Секреты только из переменных окружения; в репозитории нет ни одного.
  Пароль базы имеет умолчание `masterkey`, годное лишь для локального
  состава.
- **Rate limit на `Login` — целиком в оболочке.** Счёт требует хранилища
  и часов, а у ядра нет ни того, ни другого; правила «сколько попыток
  допустимо» в домене нет вовсе — предел операционный и стоит рядом со
  сроком жизни сессии, а не рядом с правилами домена. Прежняя редакция
  этого абзаца говорила «правило превышения — в ядре», расходясь и с
  каталогом отказов (`decided_by: shell`), и с действительностью:
  предела не существовало ни там, ни там, и двенадцать неверных паролей
  подряд проходили без единого отказа.
- Десять неудач на ник за пятнадцать минут, счёт нечувствителен к
  регистру и ведётся по любому нику — существующему или нет.
- Весь SQL параметризованный; конкатенация запросов запрещена линтером.
- Скан зависимостей в CI, ломает сборку на HIGH.
- Линия между гейтвеем и NODE-7 не выходит за пределы docker-сети.

## 15. Чего мы не делаем

- Не пишем бизнес-логику в PL/pgSQL и не дублируем её в Java.
- Не тащим EJB/WildFly.
- Не добавляем JMS/брокер — база уже шина.
- Не ведём агрегаты вручную: для объектов с идентичностью используется JPA, для дренажа outbox и проекций — сырой SQL. Раздел проходит по природе операции, а не по вкусу ([ADR-0013](adr/0013-firebird-and-orm.md)).
- Не отдаём наружу сущности Hibernate: репозитории возвращают доменные объекты, границы транзакций объявляются явно.
- Не делаем ретро-оформление ни на одной поверхности.
