# ADR-0013. Firebird вместо PostgreSQL, ORM для агрегатов

**Статус:** Принято
**Дата:** 2026-09-01
**Изменяет:** [ADR-0003](0003-outbox-over-notify.md) в части механизма уведомлений
**Отменяет** решение «без Hibernate» из [ARCHITECTURE.md](../ARCHITECTURE.md) §15

## Контекст

PostgreSQL был выбран как современный полюс системы и работает хорошо. Но
он же — единственный компонент, выбранный по привычке, а не по замыслу.

Firebird происходит от Borland InterBase — того же дома, что и Turbo Pascal.
Связь не декоративная: она объясняет, почему в системе, чьё ядро написано
на языке Borland, хранилище тоже от Borland.

При этом Firebird не обязан быть жертвой ради шутки. Он должен уметь всё,
на что опирается конструкция:

- уведомления, чтобы конвейер outbox не опрашивал базу вхолостую;
- пропуск заблокированных строк, чтобы потребители не мешали друг другу;
- живой JDBC-драйвер под Java 8, которая зафиксирована [ADR-0004](0004-corba-iiop.md).

Отдельно: в ARCHITECTURE.md было записано «без Hibernate, только видимый
SQL». Это решение принималось, когда весь доступ к данным сводился к
дренажу очереди и проекциям. После [ADR-0011](0011-pascal-domain-core.md)
у оболочки появились настоящие агрегаты с идентичностью и версией, а для
них ORM — не украшение, а стандартный инструмент.

## Проверено спайком S6

Все четыре опасения сняты измерением, а не рассуждением:

| Проверка | Результат |
|---|---|
| Jaybird 4 на Java 8 | работает, движок Firebird 5.0.4 |
| `POST_EVENT` доходит до клиента в сети compose | **15 мс** |
| Событие приходит только после фиксации | да |
| Откат не рассылает событие | да |
| Кириллица через драйвер | без искажений |
| `WITH LOCK SKIP LOCKED` | два потребителя взяли разные строки, второй ждал 8 мс |

Главное опасение было в том, что уведомления Firebird устроены как обратное
соединение: сервер подключается к клиенту сам. Это тот же класс проблемы,
на котором спотыкается CORBA со своим IOR (см. F-09 и спайк S5). В сети
compose проблема не проявилась.

## Решение

**Хранилище — Firebird 5.** `POST_EVENT` заменяет `LISTEN/NOTIFY` в роли
дверного звонка. Источником правды остаётся таблица outbox: событие Firebird,
как и уведомление PostgreSQL, не долговечно и не несёт полезной нагрузки.
Архитектура конвейера из ADR-0003 не меняется — меняется только механизм
пробуждения.

**Доступ к данным разделяется по природе операции, а не по вкусу:**

| Что | Чем | Почему |
|---|---|---|
| Агрегаты write-модели | JPA, Hibernate 5 | объекты с идентичностью и жизненным циклом; оптимистическая блокировка через `@Version` — ровно то, что требует §7 архитектуры |
| Дренаж outbox | сырой SQL | `WITH LOCK SKIP LOCKED` и пакетная выборка — операции над множествами, ORM здесь мешает |
| Проекции read-модели | сырой SQL | денормализация и агрегация; объектов тут нет |

Это стандартный раздел, а не компромисс: ORM хорош там, где есть объект с
идентичностью, и вреден там, где есть множество строк.

Hibernate 5 — последняя ветка под Java 8, и она же ровно то, как выглядел
enterprise-стек тех лет. Как и CORBA, она попадает в эпоху не случайно.

## Последствия

- Пропадает `JSONB` и сильный полнотекстовый поиск. Проекции read-модели придётся строить на обычных колонках и индексах; для ленты этого достаточно, для поиска по тексту в будущем понадобится отдельное решение.
- Пропадает полезная нагрузка в уведомлении. Не потеря: по ADR-0003 уведомление и так было только сигналом.
- Появляется зависимость от Jaybird 4. Версия зафиксирована; переход на Jaybird 5 потребует более новой Java и потому невозможен, пока в силе ADR-0004.
- Событийное соединение требует, чтобы сервер мог достучаться до клиента. В сети compose это работает, но при вынесении `events` за пределы сети понадобится проверка заново. Записано в реестр рисков.
- Hibernate добавляет способ незаметно выстрелить себе в ногу: ленивая загрузка, N+1, кэш первого уровня. Компенсируется правилом — репозитории отдают доменные объекты, а не сущности Hibernate, и границы транзакций объявляются явно.
- Знание Firebird в команде ниже, чем PostgreSQL. Это реальная цена, и она принимается сознательно.

## Рассмотренные альтернативы

**Оставить PostgreSQL.** Технически лучший вариант по возможностям и
знакомству. Отклонён потому, что он единственный выбран по привычке, а
Firebird даёт ту же функциональность и при этом объясняет сам себя.

**Berkeley DB, dBase, чистый key-value.** Отклонены: без SQL и транзакций
пришлось бы переписывать и read-модель, и outbox, и ORM стал бы невозможен.
Это не замена компонента, а другой проект.

**MUMPS, Lotus Notes.** Отклонены по той же причине, усиленной отсутствием
живых драйверов под Java 8.

**Firebird без ORM, как раньше.** Отклонено: у оболочки после ADR-0011
появились настоящие агрегаты, и вести их вручную означало бы писать свой
маленький Hibernate.
