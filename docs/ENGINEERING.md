# Инженерные стандарты

Документ обязателен к исполнению. Всё перечисленное ниже проверяется
автоматически: правило без проверки в CI считается несуществующим.

## 1. Определение готовности

Задача готова, когда выполнено **всё**:

- [ ] код покрыт тестами на своём уровне пирамиды, тесты падают без изменения и проходят с ним;
- [ ] публичный интерфейс задокументирован: назначение, владение памятью, режимы отказа;
- [ ] ошибки обработаны явно, ни один путь отказа не молчит;
- [ ] добавлены или обновлены метрики и логи, если поведение наблюдаемо;
- [ ] обновлены затронутые документы в `docs/`;
- [ ] архитектурное решение, если оно принималось, оформлено ADR;
- [ ] CI зелёный целиком, без отключённых проверок;
- [ ] в диффе нет `TODO`, `FIXME`, закомментированного кода и отладочной печати.

`TODO` без ссылки на задачу трекера запрещён линтером. Это не педантизм: в
проекте с четырьмя языками и шестью протоколами «потом разберусь» не находится
никогда.

## 2. Гейты CI (ломают сборку)

**Столбец «Чем» обязателен, и появился он не сразу.** Первая редакция
этой таблицы перечисляла одиннадцать порогов без указания, чем каждый
проверяется, — и сверка с действительностью нашла, что реализованы
два. Остальные существовали утверждением: таблица создавала уверенность,
что кто-то следит, а не следил никто.

**Гейт без проверки хуже отсутствующего.** Отсутствующий заставляет
думать при каждом изменении. Заявленный и непроверяемый — успокаивает.

| Проверка | Порог | Чем |
|---|---|---|
| Дрейф контрактов | `git diff --exit-code` после перегенерации | `./sonder check-drift` |
| Правила слоёв Java (ArchUnit) | `domain` не знает о Spring, JDBC, JAX-WS | `ArchitectureTest`, проверен на намеренных нарушителях |
| Граф модулей Pascal | без циклов, без рёбер вверх, домену запрещён ввод-вывод | `./sonder check-layers` |
| Размер бинарника NODE-7 | < 400 КБ | `./sonder check-node` |
| Бюджеты TurboCore | в пределах TURBOCORE.md §12 | `./sonder check-budgets`, числа берутся из самой таблицы |
| Переводы строк | LF по `.gitattributes` | `./sonder check-eol` |
| Согласованность контрактов | 461 проверка + самопроверка на 17 дефектах | `./sonder contracts` |
| Сгенерированный Pascal | собирается и работает под DOSBox | `./sonder check-generated` |
| Тесты TurboCore | одинаково зелёные на двух таргетах | `./sonder test` |
| Доступ по контракту | закрытые операции отвечают гостю 401, и ровно они | `GuestAccessIT` |
| Доступность веба | уровень AA, нарушений axe-core нет | `./sonder e2e-web` |
| Lighthouse | все разделы ≥ 90, медиана трёх прогонов | `./sonder lighthouse` |
| Сквозной след | один `trace_id` от заголовка до лога NODE-7 | `./sonder trace` |
| Возвращение после отказа | база и оболочка перезапускаются, система возвращается сама | `./sonder chaos` |
| Лаг read model | p99 < 1 с | `./sonder lag` |
| Имена переменных в bash | только латиницей | `./sonder check-shell` |
| Проверки умеют падать | каждая краснеет на внесённом дефекте | `./sonder falsify` |
| Время ответа входа | не различает существующий ник и несуществующий | `./sonder timing` |

Отключение проверки — только через ADR с обоснованием и сроком возврата.

### Чего в гейтах НЕТ, и почему

Перечислено ровно затем, чтобы отсутствие было решением, а не
недосмотром.

**Покрытие и мутационное покрытие `core/domain`.** Строка эта устарела
до неприменимости: после [ADR-0011](adr/0011-pascal-domain-core.md)
доменного модуля в Java НЕ СУЩЕСТВУЕТ, и его отсутствие само стало
проверкой — ArchUnit подтверждает, что в Java нет ни одного доменного
правила. Домен живёт в Pascal, где jacoco и PIT неприменимы. Покрытие
доменных правил там держится трёхслойным набором из 61 проверки и
фаззингом; чем измерить его числом на `i8086-msdos` — открытый вопрос,
и выдавать за него покрытие нативного таргета было бы подменой.

**Уязвимости зависимостей.** Не заведено. Список зависимостей закрыт и
крайне мал (Spring Boot 2.7, Hibernate 5, Jaybird 4, CXF — всё
последнее, работающее на восьмёрке), а сканер требует базы CVE в
несколько сотен мегабайт при каждом прогоне. Место этому — не в
проверке перед коммитом, а в Dependabot на репозитории.

**Форматирование.** Не заведено ни для Java, ни для Pascal. Своего
форматтера Pascal не существует, а писать его ради одного проекта
дороже пользы; расхождения в стиле ловит ревью.

**Флаки-тесты.** Прогон каждого теста двадцать раз не заведён: полный
`verify` идёт минуты, и двадцатикратный шёл бы часы. Вместо этого
`retries: 0` у Playwright — проверка, проходящая со второго раза,
сообщает о системе то же, что падающая.

## 3. Ветвление и ревью

- Транк, короткоживущие ветки, никаких долгих feature-веток.
- Каждое изменение — через PR, даже в одиночной разработке: PR это место, где живёт обоснование.
- Conventional Commits; из них собирается CHANGELOG.
- Ревью обязательно смотрит: режимы отказа, владение памятью (для Pascal), обратную совместимость контракта.

## 4. Процесс ADR

Архитектурное решение фиксируется до реализации, а не после.

- Файл `docs/adr/NNNN-краткое-имя.md`, шаблон в `0000-template.md`.
- Статусы: `Предложено`, `Принято`, `Заменено ADR-NNNN`, `Отменено`.
- Принятые ADR не редактируются по существу — они заменяются новыми.
- Ссылка на ADR обязательна в PR, который его реализует.

## 5. Документация

Три уровня, у каждого своя аудитория и свой срок жизни:

1. **`docs/`** — как система устроена и почему. Обновляется вместе с кодом, изменение проверяется на ревью.
2. **Комментарии в шапке модуля** — контракт модуля: что делает, кто владеет памятью, как отказывает.
3. **Комментарии в теле** — только про «почему», никогда про «что». Комментарий, пересказывающий код, удаляется на ревью.

Отдельное правило для Pascal: каждая функция, содержащая точку переключения
файбера, обязана объявить это в шапке. Вызывающий имеет право знать, где его
могут прервать.

## 6. Наблюдаемость как требование, а не как довесок

Новый путь исполнения считается ненаписанным, пока у него нет:

- структурного лога на входе и на отказе, с `trace_id`;
- метрики счётчика и, если путь может быть медленным, гистограммы длительности;
- понятного поведения при отказе зависимости — таймаут, ретрай или явный отказ, но не бесконечное ожидание.

## 7. Работа с отказами

- У любого сетевого вызова есть таймаут. Значения по умолчанию заданы централизованно и переопределяются явно.
- Ретраи — только для идемпотентных операций, с экспоненциальной задержкой и джиттером, с ограничением числа попыток.
- Есть предохранитель на внешние зависимости: `events` не должен добивать лежащий `core`.
- Всякое «этого не может быть» либо становится проверяемым инвариантом, либо удаляется.

## 8. Управление зависимостями

- Версии зафиксированы: `pom.xml` без диапазонов, `package-lock.json` в репозитории, версия FPC закреплена в образе.
- Новая зависимость требует обоснования в PR: что она даёт и почему нельзя без неё. Для `dosnode` внешних зависимостей нет по определению — всё пишется в проекте.
- Обновления — регулярной пачкой, не по одной случайной.

## 9. Тестовая пирамида

| Уровень | Доля | Скорость | Где |
|---|---|---|---|
| Модульные | ~70 % | мс | все юниты, Pascal — на нативном таргете |
| Свойства и фаззинг | ~10 % | секунды | домен, парсеры, кодировки |
| Интеграционные | ~15 % | секунды | Testcontainers, поддельный транспорт |
| Сквозные | ~5 % | минуты | compose, Playwright, прогон записи через NODE-7 |

Правила:

- тест не ходит в сеть за пределы своего окружения;
- тест не зависит от `sleep` — только явные ожидания условий;
- каждый найденный баг сначала становится падающим тестом, потом чинится.

## 10. Локальная разработка

Одна команда поднимает всё:

```bash
make bootstrap && make dev
```

`make verify` воспроизводит полный набор проверок CI локально. Расхождение
между локальным `verify` и CI — это дефект инфраструктуры, заводится как баг.

## 11. Эксплуатация

- Каждый юнит отдаёт `/health` (живость) и `/ready` (готовность), различая их по-настоящему.
- Runbook на каждый алерт: что случилось, как проверить, что сделать. Алерт без runbook удаляется.
- Миграции БД только вперёд и обратно совместимые: сначала выкладывается код, умеющий обе схемы.
- Восстановление: процедура резервной копии и проверенный сценарий восстановления в `docs/OPERATIONS.md`.
