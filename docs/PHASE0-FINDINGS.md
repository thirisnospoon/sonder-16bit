# Фаза 0 — журнал находок

Живой документ. Заполняется по мере прохождения спайков; на выходе заменяет
все пометки **[спайк]** в [TURBOCORE.md](TURBOCORE.md) числами и правит
затронутые ADR.

Статус на 2026-09-01: **в работе**. Пройдены S1, S1b, S2 и S5. Остался S3 —
оформление того, что уже фактически работает.

## F-01 · У DOSBox-X нет сборок под Linux

**Обнаружено:** релиз `dosbox-x-v2026.08.02` содержит артефакты только для
Windows, macOS и HX-DOS. Linux-сборок нет ни в каком виде. В Debian 12 есть
пакет `dosbox` (vanilla) и `dosbox-debug`, пакета `dosbox-x` нет.

**Влияние:** [ADR-0007](adr/0007-serial-mux-transport.md) предполагал DOSBox-X.

**Решение:** базой становится vanilla DOSBox из дистрибутива — он поддерживает
`serial1=nullmodem server:… port:…`, а это ровно то, что нужно выбранному
транспорту. DOSBox-X остаётся вариантом со сборкой из исходников и нужен только
на запасном пути R2 (ne2000 + собственный TCP/IP), где требуется эмуляция
сетевой карты.

**Последствие для плана:** спайк S2 проверяет vanilla DOSBox. Если его UART
окажется слишком медленным или неточным, сборка DOSBox-X из исходников
становится отдельной задачей с собственной оценкой.

**Статус:** принято, ADR-0007 требует правки.

## F-02 · Кросс-компилятора i8086 в дистрибутиве нет

**Обнаружено:** Debian 12 даёт `fpc` 3.2.2 с `ppcx64` и `nasm` 2.16.01, но
`ppc8086` отсутствует — `fpc -Pi8086 -Tmsdos` падает с
`Failed to execute "ppc8086", error code: 127`.

Пакет `fpc-source` содержит только `Makefile.fpc` без сгенерированных
Makefile и без верхнего уровня дерева, поэтому цели `crossall` там нет.
При этом каталог `rtl/msdos` на месте — таргет поддерживается.

**Решение:** кросс-компилятор собирается из официального
`fpcbuild-3.2.2.tar.gz` (84 МБ, downloads.freepascal.org), где есть полное
дерево и цели `crossall` / `crossinstall`. Бутстрап — дистрибутивным `ppcx64`
той же версии 3.2.2.

**Статус:** сборка запущена, результат ниже.

## F-03 · Линкер Open Watcom — 4.3 МБ из 143

**Обнаружено:** FPC для `i8086-msdos` использует NASM как ассемблер и `wlink`
из Open Watcom как компоновщик. В репозиториях Debian Open Watcom нет.

Официальные релизы `open-watcom-v2` помечены как pre-release, поэтому
`/releases/latest` в GitHub API пуст; нужный артефакт лежит в теге
`Current-build`: `ow-snapshot.tar.xz`, 143 МБ.

Linux-бинарники лежат в `./binl64/`. Нужны ровно три файла — `wlink`, `wlib`,
`wasm`, — и все они статически слинкованные ELF x86-64 без зависимостей.
Суммарно **4.3 МБ**.

```
wlink: ELF 64-bit LSB executable, x86-64, statically linked
Open Watcom Linker Version 2.0 beta Sep 1 2026
```

**Решение:** образ тянет архив в cache-mount BuildKit и извлекает из него три
файла. Весь Open Watcom в образ не попадает.

**Статус:** закрыто.

## F-04 · При кросс-сборке FPC ищет инструменты с префиксом таргета

**Обнаружено:** сборка RTL падала с `make[4]: msdos-nasm: No such file or
directory`. FPC зовёт внешние инструменты как `<os>-<tool>`.

**Решение:** `BINUTILSPREFIX=msdos-` плюс симлинки `msdos-nasm`, `msdos-wlink`,
`msdos-wlib`, `msdos-wasm` в `/usr/local/bin`.

**Статус:** закрыто.

## F-05 · RTL не собирается моделью памяти по умолчанию

**Обнаружено:** после починки F-04 сборка дошла до системного модуля и упала:

```
int64.inc(553,12) Fatal: Code segment too large
```

Модель памяти по умолчанию даёт один сегмент кода на 64 КБ, и RTL в него
не помещается. При этом `rtl/msdos/Makefile.fpc` содержит
`loaders=prt0s prt0t prt0m prt0c prt0l prt0h`, то есть стартовый код есть для
всех шести моделей — но модули компилируются под одну, задаваемую через
`OPT=-Wm<model>`.

**Первоначальный вывод оказался неверным.** Я заключил, что RTL не помещается
в модели с одним сегментом кода и что `small` с `compact` отпадают. Прямое
измерение (F-07) это опровергло.

**Решение:** RTL всё равно собирается отдельно под каждую модель и ставится в
свой префикс `/opt/fpc/<model>` — но не потому, что часть моделей не работает,
а потому, что модель обязана совпадать у RTL и у прикладного кода. Обёртка
`fpc-dos <model> …` подставляет и ключ `-Wm`, и соответствующие пути к модулям.

**Статус:** заменено выводом F-07.

## F-06 · OPT применяется и к нативной части сборки

**Обнаружено:** попытка задать модель памяти через `make crossall OPT=-Wmmedium`
уронила сборку на `rtl/linux/system.ppu`. Цель `crossall` сначала собирает
нативный компилятор и его RTL, а `OPT` уходит в обе части — для таргета
`x86_64-linux` ключа `-Wm` не существует.

**Решение:** модель памяти передаётся через `CROSSOPT`, который применяется
только к кросс-цели. Для отдельных пересборок RTL, где вся сборка и так
кросс-целевая, задаются обе переменные.

**Урок общего характера:** сборочная система FPC различает нативную и кросс-фазы
неявно. Любой ключ, добавляемый в сборку, надо осознанно относить к одной из
них, иначе диагностика уводит совсем не туда: ошибка выглядела как поломка
Linux-RTL, хотя причиной был флаг для 16-битного таргета.

**Статус:** закрыто.

## F-07 · Дело было не в модели памяти, а в RELEASE=1

**Обнаружено:** прямой перебор показал, что RTL под msdos собирается **всеми
шестью моделями памяти**, по 178 модулей в каждой:

```
ВАРИАНТ           РЕЗУЛЬТАТ  МОДУЛЕЙ
small             ОК         178
medium            ОК         178
large             ОК         178
huge              ОК         178
compact           ОК         178
small -Wh         ОК         178
medium -Wh        ОК         178
large -Wh         ОК         178
```

Настоящая причина видна в логе `crossall`: подсборка RTL вызывается как

```
make rtl_all FPC=… RELEASE=1 'OPT='
```

Цель принудительно обнуляет `OPT`, поэтому ключ модели памяти до неё не
доходил ни через `OPT`, ни через `CROSSOPT`. Собиралось всё это с релизной
оптимизацией, которая и переполняла сегмент кода.

**Решение:** сборка разбита на два явных этапа. Сначала `compiler_cycle` —
только компилятор. Затем `rtl/msdos` отдельно под каждую модель, с явным `-Wm`
и без `RELEASE`.

**Урок:** две подряд неверные гипотезы (сначала «нужна модель побольше», потом
«CROSSOPT решит») стоили двух полных сборок образа. Дешёвый прямой перебор
занял столько же, сколько одна из них, и дал однозначный ответ. При сомнениях
об окружении измерение выгоднее рассуждения — это ровно то, ради чего
существует фаза 0.

**Следствие для S1:** пространство выбора шире, чем казалось. Отпавших моделей
нет, и решение принимается по существу — по тому, что измерит спайк:

| Модель | Код | Данные | SS = DS | Что это значит для файберов |
|---|---|---|---|---|
| `tiny` | ≤ 64 КБ | общий с кодом | да | всё в одном сегменте, самый тесный вариант |
| `small` | ≤ 64 КБ | ≤ 64 КБ | да | стеки в DS просто, но 64 КБ на весь код |
| `medium` | > 64 КБ | ≤ 64 КБ | да | стеки в DS просто, куча в 64 КБ → EMS обязателен |
| `compact` | ≤ 64 КБ | > 64 КБ | нет | дальняя куча, но 64 КБ на код |
| `large` | > 64 КБ | > 64 КБ | нет | дальняя куча есть, но стеки требуют смены SS |
| `huge` | > 64 КБ | > 64 КБ | нет | то же плюс массивы больше 64 КБ |

Ожидаемый финалист прежний — `medium`, и тогда EMS из
[TURBOCORE.md](TURBOCORE.md) §4 перестаёт быть удобством и становится
обязательным. Но подтвердить это должен S1, а не ожидание.

**Статус:** закрыто.

## F-08 · RTL собран со smart-linking, нужен ключ -XX

**Обнаружено:** после установки RTL компиляция падала на
`Error: Can't open object file: system.o`, хотя модули находились. В каталоге
лежат `system.ppu` и `system.a` — объектного `system.o` нет вовсе: RTL собран
со smart-linking и упакован в архивы.

Дополнительно: цель `make -C rtl/msdos install` кладёт только `.ppu`,
объектные файлы и архивы приходится доносить из каталога сборки. И путь у неё
`units/msdos`, а не `units/i8086-msdos`, как при полной установке.

**Решение:** обёртка `fpc-dos` передаёт `-XX` (использовать smart-linking) и
`-CX` (делать смартлинкуемыми наши модули). Каталог модулей не угадывается, а
записывается сборкой в манифест `/opt/fpc/<model>/UNITDIR`.

**Проверка:** после этого все шесть моделей собирают рабочий DOS-овский `.EXE`:

| tiny | small | medium | compact | large | huge |
|---|---|---|---|---|---|
| 15016 | 14958 | 16724 | 23498 | 25552 | 29170 байт |

**Статус:** закрыто. Тулчейн работоспособен.

## S1 · Файберы — пройден, но выбор модели оказался обратным ожидаемому

Спайк прогнан по всем шести моделям памяти. На `medium` все семь проверок
зелёные: **100 000 переключений контекста**, канарейки целы, локальные данные
переживают переключение, все четыре файбера отработали по 25 000 раз.

### Измерения

| Модель | SS = DS | Указатель данных | Указатель кода | MemAvail, байт | S1 |
|---|---|---|---|---|---|
| `tiny` | да | 2 | 2 | 35 086 | пройден |
| `small` | да | 2 | 2 | 52 498 | пройден |
| `medium` | да | 2 | 4 | 52 366 | пройден |
| `compact` | **нет** | 4 | 2 | **597 516** | провал: SS ≠ DS |
| `large` | **нет** | 4 | 4 | **596 188** | провал: SS ≠ DS |
| `huge` | **нет** | 4 | 4 | **595 020** | провал: SS ≠ DS |

Глубина стека на `medium`: **38 байт** у простого файбера, **224 байта** у
файбера с рекурсией на шесть уровней и массивом из восьми слов на кадр.
Заложенные в [TURBOCORE.md](TURBOCORE.md) §12 три килобайта на файбер — с
большим запасом.

### Что это значит

Компромисс теперь измерен, а не предположен, и он резкий: **разница по доступной
памяти — 11 раз**.

- Модели с `SS = DS` (`tiny`, `small`, `medium`) дают конструкцию файберов ровно
  такой, как задумано в [ADR-0008](adr/0008-cooperative-fibers.md): стеки статическим
  массивом в сегменте данных, переключается только SP. Но на всё про всё — около
  **52 КБ**. При двенадцати файберах по 3 КБ на стеки уходит 36 КБ, и на кучу,
  буферы и глобальные данные остаётся около 16 КБ. EMS становится не просто
  обязательным, а несущим: через него пойдёт практически всё.

- Модели с дальними данными (`compact`, `large`, `huge`) дают около **596 КБ**
  напрямую адресуемой кучи — примерно 49 КБ на сессию при двенадцати сессиях.
  Но `SS ≠ DS`, и переключать придётся не только SP, но и SS.

**Ожидание не подтвердилось.** Я записывал `medium` как ожидаемого финалиста.
Измерение показывает, что цена этого выбора — вся память проекта, а цена
альтернативы — одна дополнительная пара инструкций в одной ассемблерной
процедуре. Смена SS вместе с SP локализована в `ContextSwitch`; работа с EMS,
наоборот, размазывается по каждому выделению памяти и по каждому переключению
контекста, потому что странице надо быть отображённой.

**Предварительный вывод:** `large` выглядит предпочтительнее. Проверено
отдельным прогоном — см. ниже.

## S1b · Файберы в дальней куче — пройден, модель выбрана

Вариант `ContextSwitch` со сменой `SS` вместе с `SP`, стеки из дальней кучи,
прогон на `large`. Все семь проверок зелёные.

| Показатель | medium | large |
|---|---|---|
| MemAvail на старте | 52 366 Б | **599 628 Б** |
| Размещение стеков | статический массив в DS | дальняя куча, свой сегмент у каждого |
| Сегменты стеков | — | 3482, 3547, 3613, 3678 |
| SS / DS | 1570 / 1570 | 2458 / 2133 |
| Переключений | 100 000 | 100 000 |
| Канарейки | целы | целы |
| Глубина стека, байт | 38 / 38 / 224 / 56 | 38 / 38 / 220 / 42 |
| Размер бинарника | 21 002 Б | 30 390 Б |
| Память после освобождения | — | вернулась байт в байт |

Утечки нет: `MemAvail` до выделения стеков и после их освобождения совпал
точно — 599 628 в обоих замерах.

**Решение принято:** модель памяти проекта — `large`. Оформлено в
[ADR-0010](adr/0010-large-memory-model.md), изменяет ADR-0008 в части
размещения стеков. EMS понижен с несущей конструкции до резерва, спайк S4
теряет приоритет.

**Замечание о процессе.** За время спайка я дважды сделал неверный вывод из
рассуждения (F-05, «ожидаемый финалист medium») и оба раза его опровергло
прямое измерение, стоившее меньше, чем одна лишняя пересборка образа. Оба
неверных вывода оставлены в документе намеренно: они показывают, почему
фаза 0 состоит из экспериментов, а не из проектирования.

## S2 · Транспорт — пройден, потолок и накладные измерены

Vanilla DOSBox, `serial1=nullmodem`, DOS-сторона работает эхо-ответчиком и
программирует 16550 напрямую через регистры, без INT 14h — как будет делать
`tcport`. Все замеры на хосте: у него микросекундные часы, у DOS тик BIOS в 55 мс.

### Скорость

| Делитель | Номинал 8N1 | Измерено на направление | Отношение |
|---|---|---|---|
| 1 (115200 бод) | 11 520 Б/с | **11 503 Б/с** | 0.999 |
| 12 (9600 бод) | 960 Б/с | **960 Б/с** | 1.000 |

**DOSBox честно эмулирует скорость по делителю UART.** Оба прогона отразили
ровно 117 554 байта, переполнений приёмника ноль, ошибок линии ноль. Линия
полнодуплексная: каждое направление несёт свои 11.5 КБ/с независимо.

Делитель 1 — предел стандартного 16550. Поднять потолок в рамках выбранного
транспорта нельзя.

### Фиксированные накладные — важнее скорости

| Кадр | p50, мс | Чистая передача, мс | Накладные |
|---|---|---|---|
| 1 Б | 13.32 | 0.09 | 13.2 |
| 64 Б | 12.97 | 5.6 | ~13 |
| 128 Б | 13.13 | 11.1 | ~13 |
| 256 Б | 25.02 | 22.2 | ~13 |
| 512 Б | 48.95 | 44.4 | ~13 |
| 1024 Б | 97.10 | 88.9 | ~13 |
| 2048 Б | 181.82 | 177.8 | ~13 |

Накладные на круг — **около 13 мс и не зависят от скорости линии** (13.07 мс при
115200, 12.77 мс при 9600). Это гранулярность обслуживания порта эмулятором, а
не время передачи.

**Следствие:** кадр меньше **151 байта** целиком съедается накладными. Кадр в
один байт стоит столько же, сколько кадр в сто двадцать восемь.

### Что это означает для конструкции

> Пункты ниже переписаны после [ADR-0011](adr/0011-pascal-domain-core.md):
> линия несёт не отрисовку экранов, а команды и решения. Сами измерения от
> этого не изменились, изменились выводы из них.

1. **11 520 Б/с — потолок записи всего приложения.** NODE-7 стал доменным ядром, и каждая операция записи проходит через линию: команда со состоянием туда, решение обратно. Чтение через линию не идёт вовсе и этим потолком не ограничено.
2. **Порядка десяти операций записи в секунду.** Круг — это примерно 600–800 байт в обе стороны плюс 13 мс накладных, то есть около 90 мс. Конвейеризация файберами улучшает цифру примерно вдвое. Это главное узкое место системы, и оно измерено, а не оценено.
3. **Объём передаваемого состояния — теперь параметр производительности.** Каждый лишний байт в объявлении состояния команды напрямую вычитается из пропускной способности. Контракт `decider-v1.wsdl` должен объявлять минимально достаточное состояние, и это предмет ревью, а не вкуса.
4. **Мультиплексор обязан пакетировать.** Если каждая команда получает свой кадр, шестнадцать одновременных команд стоят 16 × 13 = 208 мс чистых накладных за круг — больше, чем передача самих данных. Один кадр, несущий сегменты нескольких каналов, убирает эту цену. Прямое требование к `tcframe` и `tcmux`.
5. **Размер кадра — 512 байт полезной нагрузки.** Накладные 23 % против 37 % у 256 байт, линия занята не дольше 57 мс за раз. Значение из [TURBOCORE.md](TURBOCORE.md) §12 подтверждено измерением, а не угадано.
6. Простой опрашивающий цикл на максимальной скорости не теряет ни байта. Прерывания UART для приёма не нужны, во всяком случае на этом уровне нагрузки.

### Две ошибки обвязки, стоившие двух прогонов

**Рукопожатие.** DOSBox открывает сокет на старте эмулятора, задолго до запуска
программы, а инициализация UART очищает FIFO. Всё, что хост отправил за это
время, теряется молча: приёмник переполняется, а биты ошибок сбрасываются первым
же чтением LSR. Добавлен байт готовности от DOS-стороны. Это не костыль спайка —
гейтвей столкнётся ровно с тем же, и требование попадает в протокол.

**Проверка готовности сокета подключением.** Обвязка проверяла, что хост слушает,
устанавливая пробное соединение. Оно занимало единственный слот `listen(1)`,
`accept()` возвращал его вместо DOSBox, и обмен шёл в закрытый сокет. Заменено на
файл-маркер.

**Статус:** пройден.

## F-09 · Тип string в CORBA не принимает кириллицу

**Обнаружено:** первый прогон S5 упал на передаче структуры с русским текстом:

```
org.omg.CORBA.DATA_CONVERSION: vmcid: OMG minor code: 1
  Character does not map to negotiated transmission code set
Caused by: java.nio.charset.UnmappableCharacterException: Input length = 1
```

Тип `string` в CORBA байтовый и ограничен согласованной кодировкой передачи.
Русский текст в него не проходит.

**Чем опасно:** ошибка не видна ни при компиляции IDL, ни при генерации стабов,
ни на ASCII-данных. Она возникает в рантайме, когда в поле впервые попадает
непустая кириллица — то есть на первом же реальном пользователе.

**Решение:** любое поле IDL, несущее человеческий текст, объявляется `wstring`.
Идентификаторы остаются `string`: они ASCII по контракту, и это фиксируется
комментарием в IDL. Правило уходит в [ADR-0004](adr/0004-corba-iiop.md) и в
чек-лист ревью контракта.

**Проверено:** после перевода полей в `wstring` строка `Ёжик, ñ, 中文, ß`
проходит в обе стороны без искажений.

**Статус:** закрыто.

## S5 · CORBA между контейнерами — пройден

Два контейнера в одной сети compose, JDK 8, `idlj` из состава JDK, IOR
публикуется через общий том.

| Проверка | Результат |
|---|---|
| IOR опубликован | да, 376 байт |
| Вызов дошёл до соседнего контейнера | **да** |
| Структура и кириллица | без искажений (после F-09) |
| Не-ASCII в обе стороны | без потерь |
| Исключение IDL | доставлено как исключение, а не как обрыв связи |
| Латентность `ping` | p50 **1.973 мс**, p99 **9.639 мс**, 200 вызовов |

**Главный риск снят.** Опасение состояло в том, что ORB зашьёт в IOR адрес,
по которому видит сам себя изнутри контейнера, и клиент пойдёт по
недостижимому имени. Лечится свойством `com.sun.CORBA.ORBServerHost`, которому
задаётся имя сервиса в сети compose. Без него конструкция не работает, с ним
работает без оговорок.

**Следствие для производительности.** `events` дёргает `core` по IIOP на каждое
обогащаемое событие, и латентность p50 в 2 мс даёт потолок дренажа outbox около
**500 событий в секунду**. Это в пятьдесят раз выше потолка записи (10 операций/с
через последовательную линию), то есть CORBA узким местом не является и в
обозримой перспективе не станет.

**Замечание о процессе.** При правке спайка я затёр файл клиента: `write_text`
усекает файл перед записью и упал на кодировании суррогатной пары, оставив
ноль байт. Ровно от этого в серверном коде спайка защищена публикация IOR —
запись во временный файл и переименование. Приём стоило применить и к
инструментальным скриптам.

**Статус:** пройден.

## F-10 · Python на Windows ломает shell-скрипты переводами строк

**Обнаружено:** после правки скрипта спайка через `pathlib.write_text` прогон
в контейнере упал:

```
run.sh: line 17: $'\r': command not found
run.sh: line 36: syntax error near unexpected token `$'do\r''
```

`write_text` на Windows транслирует `\n` в `\r\n`. Для Markdown и Python это
безвредно, для shell-скрипта — фатально: интерпретатор в Linux считает `\r`
частью команды.

Проверка всего дерева нашла ещё три файла с CRLF: исходник спайка на Pascal,
Java-файл и Python-модуль.

**Решение:** добавлен `.gitattributes` с `eol=lf` для всего исполняемого и
всего текстового, что попадает в контейнеры. Инструментальные скрипты пишут
файлы байтами, а не через `write_text`.

**Общее правило проекта:** разработка идёт на Windows, исполняется всё в
Linux-контейнерах. Любой инструмент, порождающий файлы, обязан считаться с этой
границей — она проходит через весь проект и будет напоминать о себе регулярно.

**Статус:** закрыто.

## S3 · Headless-прогон в CI — пройден

Оформлена переиспользуемая обвязка `ops/ci/run-dos-tap.sh`: запускает
DOS-бинарник под DOSBox без дисплея, со сторожевым таймером, и выносит вердикт
по TAP-файлу в примонтированном каталоге.

**Обвязка различает три исхода**, которые наивная проверка `grep 'not ok'`
спутала бы:

| Исход | Признак |
|---|---|
| Программа не отработала вовсе | TAP-файла нет |
| Программа упала на середине | выполнено проверок меньше, чем объявлено в плане `1..N` |
| Программа отработала и провалилась | есть строки `not ok` |

Второй случай — самый коварный: при обрыве на середине в отчёте могут остаться
одни только `ok`, и без сверки с планом прогон выглядел бы успешным.

### Измерение устойчивости

Один и тот же бинарник (S1b, модель `large`, 100 000 переключений контекста)
прогнан **20 раз подряд**:

| Показатель | Значение |
|---|---|
| Успешных прогонов | **20 из 20** |
| Различных подписей результата | **1** |
| Время прогона | 2715–2949 мс, разброс 8 % |
| Суммарное время | 58 с |

Результат детерминирован. Опасение из R3 — подвисания, потерянные коды
возврата, флак — на этом объёме не подтвердилось.

### Две ошибки в самом спайке

**Подставил не тот бинарник.** Первый прогон собрал `s1.pas` моделью `large`,
хотя `s1.pas` требует совпадения `SS` и `DS`. Все 20 прогонов честно провалились.
Обвязка при этом отработала правильно: поймала семь `not ok` и не выдала их за
успех. Неприятная ошибка оказалась полезной проверкой самой обвязки.

**Подпись включала номер прогона.** Итоговая строка обвязки содержит имя
прогона, и подпись получалась уникальной у каждого запуска — детерминизм
выглядел бы нарушенным при полностью стабильном результате. Подпись считается
только по нумерованным строкам TAP самой программы.

**Статус:** пройден.

## S6 · Firebird как замена PostgreSQL — пройден

Firebird 5 происходит от Borland InterBase, то есть из того же дома, что и
Turbo Pascal. Проверялось, не приходится ли платить за это связностью
архитектуры.

| Проверка | Результат |
|---|---|
| Jaybird 4 на Java 8 | работает, движок **5.0.4** |
| `POST_EVENT` доходит до клиента в сети compose | **8–15 мс** |
| Событие приходит только после фиксации | да |
| Откат не рассылает событие | да |
| Кириллица через драйвер | без искажений |
| `WITH LOCK SKIP LOCKED` | A взял 10, B взял 10 **других**, ждал 6 мс |

**Главное опасение снято.** Уведомления Firebird устроены как обратное
соединение: сервер подключается к клиенту сам. Это тот же класс проблемы, на
котором спотыкается CORBA со своим IOR (S5). В сети compose она не проявилась,
причём без дополнительной настройки — в отличие от CORBA, которой понадобился
`ORBServerHost`.

**Что теряется по сравнению с PostgreSQL:** `JSONB` и сильный полнотекстовый
поиск. Проекции read-модели строятся на обычных колонках и индексах; для ленты
этого хватает, для поиска по тексту понадобится отдельное решение.

**Что не теряется:** полезная нагрузка в уведомлении. Её не было и раньше —
по [ADR-0003](adr/0003-outbox-over-notify.md) уведомление всегда было только
сигналом, а источником правды остаётся таблица outbox.

**Замечание об API.** Первая сборка упала: `setServerName` и `setPortNumber`
появились в Jaybird 5, а нам нужен Jaybird 4 — пятая версия требует более
новой Java, зафиксированной [ADR-0004](adr/0004-corba-iiop.md). Правильные
имена — `setHost` и `setPort`. Мелочь, но показательная: выбор Java 8 тянет
за собой версии всех драйверов, и это стоит проверять до, а не после.

**Решение:** [ADR-0013](adr/0013-firebird-and-orm.md) — Firebird становится
хранилищем, а доступ к данным разделяется: JPA для агрегатов, сырой SQL для
дренажа outbox и проекций.

**Статус:** пройден.
